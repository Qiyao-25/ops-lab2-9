# fsync 基线跨日期复测

## 结果与分析

**现象与处理：原始基线保留，本次作为独立复测。** 最初三轮均值约 1.280 ms；11 月 2 日留存复测、用户本次提供的数据及 11 月 3 日新增六轮均较慢。新增六轮 mean 的平均值为 **1.678833 ms**，比最初增加 **31.19%**；对应单写者串行 fsync 估算上限约 **596 次/秒**，比原先约 781 次/秒下降 **23.78%**。这表明已观测到跨日期的性能变化，不能据此认定原先数据错误，也不能将某次结果当作主机永久不变的能力。

**新增复测条件。** 北京时间 2026-11-03 12:21:30 开始监控，12:21:40～12:22:20 执行两组三轮 `bin/enrolld -bench-fsync 2000`，两组之间空闲约 20 秒，12:22:25 结束监控。命令未绑核，与最初基准命令一致；测试前及每轮开始前均确认没有其他 enrolld/loadgen 进程。保留已有监控及系统服务，没有重启、清缓存或变更磁盘配置。启动时主机负载很低，数据目录仍在 `/dev/vda1` 的 ext4 上，磁盘已用 32%，无 Swap。详细条件见 `environment.json`；同步采集 `vmstat -w -t 1`、`iostat -dx -t 1 vda`、`pidstat -d -p ALL 1`。

**资源证据与限制。** 仅选取完整落在空载窗口或单轮基准窗口内的一秒区间，排除 vmstat/iostat 首组开机以来平均值和跨越测试边界的样本；空载各 9 个、负载各 14 个样本，行号及区间结束时间见 `selected-samples.csv`。这是独立复测的取样说明，不替换前文任务 0 的连续 10 秒观测。原始日志不修改，派生范围见 `summary.json`：

|---|---|---|

| vmstat wa / st | wa 0～1%，st 0% | wa 44～47%，st 0% |
| iostat w_await | 0～1.00 ms | 0.51～0.56 ms |
| iostat f_await | 0～0.17 ms | 0.07～0.12 ms |
| iostat w/s / f/s | w/s 0～70，f/s 0～6 | w/s 1708～1874，f/s 1136～1249 |
| iostat aqu-sz / %util | 0～0.05 / 0～0.60% | 1.03～1.09 / 93.60～97.00% |

本次 CPU 计算占用较低、无可见 steal 时间，等待主要出现在同步 I/O 路径；与前文 10 月 29 日独立观测的 `w_await=0.41～0.43 ms`、`f_await=0.03～0.04 ms` 相比，设备层写及 flush 耗时也有所上升，方向与应用 fsync 变慢一致。但这不是严格受控的跨日期因果实验，且设备 await 与应用 fsync 不一一对应，不能直接相加或替代。`%util` 接近 100% 也不能单独证明云盘已达到 IOPS 或吞吐上限。

**可能原因，尚未确定唯一根因：**

1. 云存储后端、存储网络或实例存储 QoS 的可用性能可能变化。华为云说明云盘性能受实例规格、负载、网络环境及数据块大小等影响，见[云硬盘类型及性能介绍](https://support.huaweicloud.com/intl/zh-cn/productdesc-evs/zh-cn_topic_0014580744.html)。本次设备 await 变长与此类变化相容，但没有平台侧时延、限流或后端监控，不能断言发生了宿主机争用、限流或突发额度耗尽。
2. 文件系统日志提交、回写和同步缓存路径也会影响 fsync。[fsync 手册](https://www.man7.org/linux/man-pages/man2/fsync.2.html)说明其需等待设备报告完成，并涉及文件数据及相关元数据。应用 mean、设备写 await 和 flush await 同方向变化，支持“同步 I/O 路径变慢”，不能进一步区分内核、文件系统与存储后端各自贡献。
3. 后台监控、日志和云代理存在少量写入，本次没有隔离这些服务。`pidstat-io.log` 捕捉到日志进程、代理及采样工具的活动，因此不能完全排除本机写入干扰；没有证据证明它们解释了全部约 31% 的变化。文件系统 jbd2 的写入也可能由基准本身触发。采集父进程 Python 的 I/O 包含已等待退出的基准子进程，分析已排除该父进程，避免将子进程累计计数误判为额外后台写入；依据见 [/proc/PID/io 手册](https://www.man7.org/linux/man-pages/man5/proc_pid_io.5.html)。
4. 已检查当前仓库与最初基线提交之间的 `cmd/enrolld/commit.go`、`main.go`，没有受版本控制的源码差异。但当前二进制构建信息标记 `vcs.modified=true`，旧基线未留存可比的二进制 SHA256，不能声称两次可执行文件逐字节相同。本次二进制 SHA256 在六轮前后保持一致，见 `environment.json`。

**对报告结论的影响。** 最初基线、W1/W2/W3 原始结果及测前预测全部保留；原 W1 实验自身记录的 `fsync_mean_ms=1.28882` 与当时约 1.28 ms 的基线接近，说明旧实验内部有相应证据。新增复测说明容量估算具有时间和环境条件，不能把旧约 781 次/秒直接当作现在的保证。后续如重跑写路径实验，应在同一时段重新测基线并写下新的预测，将新一轮完整结果单独归档；本次约 596 次/秒仅为单写者串行 fsync 的粗估，不是已验证的 HTTP 成功吞吐或满足延迟目标的容量，也不直接适用于组提交模式。
